## 一、实现补齐

### Q1 `ContractFile` 仍停留在骨架，JSON 无处可解

**缺口**：契约文件是本中间件唯一的结构化输入（九维：输入/输出维数、输入字段表、动作空间），但此前 `ContractFile::load` 未实现，而项目又**明确不引入第三方 JSON 库**（内核侧零第三方链接是架构硬规则）。Agent 侧拿不到契约就装不了模型，整条决策链在第一拍即断。

**实现**：新增 `common/include/JsonUtil.h`——header-only 的递归下降解析器 + 序列化器（504 行），随后 `ContractFile.cpp`（177 行）在其上完成解析。

| 项 | 做法 | 依据 |
|---|---|---|
| 值模型 | 六类：`Null` / `Bool` / `Number` / `String` / `Array` / `Object` | 覆盖契约文件用到的全部结构 |
| 错误处理 | **解析不抛异常**，非法一律返回 `false` | 调用方是装载路径，异常会穿透到服务线程；返回码与全项目 `bool` + `Reason` 口径一致 |
| 数字文法 | 收紧到 JSON 规范：无前导 `+`、多位整数不以 `0` 开头、小数点后至少一位 | 宽松解析会放过 `01` / `1.` / `+1` 这类噪声，错误延后到维度校验才爆，难以定位 |
| 序列化 | **整数按整数形态输出**（`1` 而非 `1.0`）；键序按 `std::map` | 保证往返稳定，便于测试逐位对拍 |
| 依赖 | 只用 `<cstring>` / `<cstdlib>` 等标准头，补齐 `std::strlen` / `std::strtod` 限定 | 保持零第三方 |

`ContractFile.cpp` 侧另有三点：

- **三道校验分工**（D-25）：解析只管文法与取值域，维度一致性留待 Agent 侧第 1、2 道校验；
- **临时对象**：先填 `Contract tmp`，`parseInputFields` 与 `parseActions` **全过才 `std::move` 提交**——中途失败不留下半成品契约；
- **额外收紧**（设计未明写，属实现层补漏）：`source ∈ {task, system}`、`device ∈ {cpu, npu}`。二者都是枚举语义，放过去会在特征编码期才炸。

### Q2 `DecisionMaker` 的 S2 特征编码缺位

**缺口**：S2 是「系统状态 + 任务信息 → 归一化特征向量」的唯一转换点，也是 D-28（**提交命名特征、不提交向量**）的落点。缺了它，`makeDecision` 只能返回占位决策，DQN 推理拿不到任何输入。

**实现**：`DecisionMaker.cpp`（221 行）匿名 namespace 内新增三个助手——`readSystemField` / `readField` / `normalize`，编码循环严格**按 `contract_.inputFields` 的顺序**逐字段取值，保证与训练期字段序一致（顺序错位等价于喂错模型）。

`normalize` 的形状：

```cpp
const double span = field.rawMax - field.rawMin;
const double unit = (span == 0.0) ? 0.5 : (raw - field.rawMin) / span;
const double v = field.min + unit * (field.max - field.min);   // 再做 [0,1] 夹取
```

两处刻意设计：**退化区间**（`span == 0`，常量特征）取中值 `0.5` 而非判失败——常量特征在采集侧是常态；**夹取**放在仿射之后而非之前——先夹再仿射会把「轻微越界」与「严重越界」压成同一个值，丢掉梯度。

### Q3 `ServiceInterface::handleFrame` 未按四键外壳返回

**缺口**：服务接入层是外部可见的唯一契约面，此前 `handleFrame` 未实现；而错误码到 `Reason` 的映射若不集中，各分支各写一份必然漂移（D-33 要的就是**唯一映射**）。

**实现**：`ServiceInterface.cpp`（252 行）匿名 namespace 内集中五个助手——`codeOf` / `shell` / `fail` / `encodeAction` / `encodeSnapshot` / `decodeTaskAsk`。

`codeOf` 是 D-33 的**唯一映射表**，逐 `Reason` 枚举列出（含 `none → 0`），末尾兜底 `return 2002`。所有失败分支一律经 `fail(code, message)` 走 `shell` 组装四键 `{ok, code, message, data}`，**不允许任何分支手写字面量**。

### Q4 `UDSService` / `ONNXruntime` 本机编不了，长期空着

**缺口**：这是全项目仅有的两个平台相关类——`UDSService` 依赖 `epoll` / `AF_UNIX`，`ONNXruntime` 硬依赖 onnxruntime SDK。二者在本机（Windows + 无 SDK）**既无头文件也无库**，此前只能空着，等于协议层与推理层完全没有可交付物。

**实现**：两个 .cpp 按 POSIX / Ort C++ API **盲写完成**，并以两套**最小仿真头**过 `-fsyntax-only` 语法检查：

| 类 | 行数 | 关键实现点 |
|---|---|---|
| `UDSService.cpp` | 429 | 帧级故障（魔数 / 版本 / 长度越界）以**空串表达断连**；未知 `type` 回 1002 且**不断连**；半帧 5 s 超时**只剪 `inbuf` 非空**的连接（D-29）；`maxConn` 超限立即关新连接；粘包半包按 `length` 切帧 |
| `ONNXruntime.cpp` | 177 | **先建后换**（`catch (Ort::Exception)` 保旧会话）；输入形状恒 `{1, n}`；D-31 超时用**条件变量** + 看护线程 `SetTerminate()`，**推理提前结束不白等**，`Run` 返回后**必须 `join`** |

仿真头只用于语法检查，**不参与构建**：`test/posixshim/`（`sys/{socket,un,epoll,eventfd}.h` + 用 `#include_next` 接续的 `fcntl.h`，112 行）、`test/onnxshim/onnxruntime_cxx_api.h`（106 行，模板化 `CreateTensor<T>` / `GetTensorMutableData<T>`）。

> **注意**：语法通过 ≠ 行为正确。这两个类的**运行期行为仍须在装好 SDK 的 openEuler 容器 / 真机上验证**，本报告不宣称已验证。

## 三、设计改动：档位表改为懒加载（唯一一处改设计）

### Q6 服务线程先于监控线程到达时，`setFreq` 假失败

**问题**：`freqTable` 由 `getCPUInfo` / `getNPUInfo` 装配，`setFreq` 只取快照、为空即判 `Reason::freqUnavailable`（3002）。后果：服务线程可能在**任何一次采集发生之前**就收到调频请求——此时设备完全可读，只是「还没被读过一次」，却被判成「频率不可用」。这是把**状态缺失**误判成**能力缺失**，属假失败。

**处理**：`CPU` / `NPU` 各加一步 S0（实现层各 6 行），口径与 `getCPUInfo` S1 完全一致——**持锁只看一眼是否为空，读文件仍在锁外**；装表仍失败时才落到 S1 的 3002，那才是真失败。

| 位置 | 改动 |
|---|---|
| `design.md` §3.12 构造行 / S5 | 「由首次 `getCPUInfo` 懒加载」→「首次 `getCPUInfo` **或** `setFreq` 谁先到谁装表」 |
| `design.md` §3.12 `setFreq` 方法行 | 前置增加「**确保频率表已读**（空则调 `readFreqTable()` 懒加载）」 |
| `design.md` §3.12 算法步骤 | 新增 S0，S1 改为「表**仍**为空 → 3002」 |
| `design.md` §3.13 | 同构四处一并改（构造行 / S4 / `setFreq` 方法行 / S0） |
| `system/src/CPU.cpp`、`NPU.cpp` | `setFreq` 开头加懒加载块；构造注释同步 |
| `system/include/CPU.h`、`NPU.h` | 文件头设计依据与 `setFreq` 方法注释同步 |
| `test/system_test.cpp` | 用例 11 从「固化旧行为」翻转为「验证新行为」（未经采集直接 `setFreq` → 成功且确实写了节点）；用例 10 补 NPU 侧 3002，与用例 11 的假失败形成对照 |
